## Findings

### F1 — `chatId` sentinel drift (stage-1/stage-2) — **FIXED**

`src/ports/conversations/capture-conversation.ts:126` (pre-fix) constructed `chatId: msg.chat?.id ?? 0` — the Owner's real (non-zero) chat id — while `sad.md` §4 pillar 3, §6, §11, §12 and `data-model.md` all commit to the composite no-source-chat sentinel `chatId: 0, chatUsername: null`. Not an AC-06 break (link-building keys off `chatUsername` only), but a contradiction of a repeatedly-documented, binding design decision, and it silently invalidated the `sad.md` §11 risk-mitigation note ("code that reads `source_snapshots` outside the existing helpers could misinterpret `chatId=0`" — false in shipped code, since `chatId` was never actually `0`).

**Resolution (user decision):** fix the code to match the documented contract.
- `capture-conversation.ts:126` now writes `chatId: 0` unconditionally.
- Added an assertion in `capture-conversation.test.ts` locking `chatId === 0` / `messageId === 0` for a typed capture.
- Reconciled the `source-handler.test.ts` AC-06 fixture (`chatId: 777` → `chatId: 0`) so it matches the sentinel it claims to test.

Verified: full suite re-run green (260/260) after the fix.

### F2 — Trim inconsistency between recognized-command checks and the new plain-text branch — **Not an issue (out of scope)**

`router.ts` matches `/settings`, `/list`, `/stats` with untrimmed `msg.text.startsWith(...)`, while the new plain-text branch trims first. A whitespace-padded recognized command (`"  /list"`) falls through to the new branch instead of running its handler — but AC-04 only requires that command-shaped (trimmed) text is never captured as a new reminder, which still holds (`router-auth.test.ts:301-307`). The untrimmed command checks predate this feature and are untouched by the diff — pre-existing behavior, outside this feature's blast radius (spec §3 non-goal: "Any change to the forwarded-message capture flow — untouched by this feature").
